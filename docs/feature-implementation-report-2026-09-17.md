## 1. 系统日志

### 1.1 板端核验（已完成，详见 `docs/system-log-audit-2026-09-17.md`）

| 日志源 | 写入 | 轮转 | 占用 | 判定 |
|---|---|---|---|---|
| `pps_tod`（`/var/log/pps_tod/`） | ✅ | ✅ 按天 + gzip + 100MB 封顶 | 1.4 MB | **健康** |
| lighttpd | ✅ | ❌ 从未轮转（目录 mtime 停在 2019-02-14） | 1.3 MB | 暂不紧急 |
| rsyslog（daemon/syslog） | ✅ | ❌ **记账失真，实际未轮转** | **678 MB** | **需处理** |
| journald | ✅ | — | 19.6 MB（易失） | 健康 |

**三个根因**（按严重度）：

1. **hostapd 失败刷屏**：`/etc/hostapd/hostapd.conf` 不存在，`hostapd.service` enabled 且卡在 `activating`，
   每 2 秒失败一次写 4 行 → **约 10 MB/天**。`daemon.log` 共 3 474 797 行，其中
   **hostapd 相关 1 973 338 行（56.8%）**。
2. **logrotate 日期记账失真**：板子无 RTC 电池 → 时钟在 2017/2019/2022-12/2026-09 间跳变
   （`who -b` 显示启动时刻 2017-01-01）→ `/var/lib/logrotate/status` 里所有条目都是同一次开机时刻
   `2026-9-16 18:00`，`logrotate -d` 因此认为"刚轮转过"，跳过；而 `daemon.log` 里躺着 2019-02-14 的内容。
3. **cron 服务未运行**（`systemctl is-active cron` = inactive，无 crond/anacron 进程）
   → `/etc/cron.d/pps_tod_rtc`（**RTC 每 6h 持久化**）与 `/etc/cron.daily/*` 全部不执行，
   与根因 2 形成恶性循环（时钟不写回 RTC，下次开机又是错的）。

**建议处置**（未执行，建议由你确认）：

```sh
systemctl disable --now hostapd            # 立即止住 10MB/天；若确需 AP 则补 hostapd.conf
logrotate -f /etc/logrotate.d/rsyslog      # 强制轮转一次
truncate -s 0 /var/log/daemon.log /var/log/syslog.1   # 回收约 650 MB
# 在 /etc/logrotate.d/rsyslog 的 daemon 组加 maxsize 50M，防单服务再次撑爆
systemctl enable --now cron                # 让 RTC 持久化恢复执行
```

## 2. 每个授时网口的授时监测

### 2.1 为什么需要新组件

chrony 3.4 **没有按接口的统计**（`serverstats` 仅 5 个全局计数器），所以"哪个口在被谁请求、是否在应答"
无法从 chronyd 得到。原方案只有 iptables 端口级包计数。

### 2.2 实测确定的两条数据通路

在板子上做了决定性验证，得到一个**反直觉但关键**的结论：

| 方向 | AF_PACKET 能否看到 | 结论 |
|---|---|---|
| 入向（请求） | ✅ `eth0 HOST(IN) ... x7` / `eth1 HOST(IN) ... x5` | 用 AF_PACKET，可拿到源 IP 与网口 |
| 出向（应答） | ❌ **看不到**（注入 9 包，chronyd 实发 9 包，AF_PACKET outgoing=0） | **改用 iptables OUTPUT 计数** |

所以守护进程走两条路：**AF_PACKET 抓入向**（客户端身份）+ **iptables OUTPUT 计数**（每口应答量）。
内核 4.19 无 `PACKET_IGNORE_OUTGOING`（4.20+ 才有），出入向靠 `sockaddr_ll.sll_pkttype` 区分。

### 2.3 新增组件

**`ntp_nic_monitor.c`**（新，常驻，root）
- 单个 `AF_PACKET/SOCK_DGRAM/ETH_P_IP` 套接字，非阻塞排空（阻塞会把周期写盘饿死）
- 每口统计：请求数、**有效 NTP（mode 3）数**、应答数（iptables delta）、近 1 小时每分钟桶
- 客户端表：`(ifindex, src_ip)` 开放寻址哈希，**1024 槽固定、零动态分配**；1 小时未活跃淘汰；每口 Top 32
- 每 5 秒原子写 `/var/db/ntp_nic.json`（tmp+rename，读方永不会看到半个对象）
- iptables 规则用 `-C || -I` **幂等**创建（实测重启不新增规则）；**启动时记录基线**，
  使 `rsp` 与 `req` 同为"自进程启动"口径——否则 iptables 计数跨重启存活会让应答率失真
- 日志走 journald，不新增日志文件与轮转负担

**`ntp-nic-monitor.service`**：root、`Restart=always`、开机自启、`NoNewPrivileges`/`ProtectSystem=full` 加固

**`src/ntpmon.c` 扩展**：把守护进程的 JSON **原样嵌入** stats 响应的 `nic` 键（无需在 C 里写解析器），
拼接 `ok`/`age_s`；文件缺失降级 `{"ok":false}`；**超过缓冲区时降级为 `too_large` 而不是输出被截断的非法 JSON**

**前端**：「服务监控及报警」Tab 新增两块面板
- 「各网口授时服务状态」：网口 / 请求 / 有效 NTP / 应答 / 应答率 / 客户端数（应答率低于 95% 标黄、80% 标红）
- 「客户端明细」：按网口筛选，客户端 IP / 请求数 / 有效 NTP / 最后活跃，按请求数排序

## 4. TOD 时码比对

### 4.1 缺口（已核实源码 `/mnt/c/Users/YAO/Desktop/codex_store/PPS_TOD/pps_tod.c`）

1. **没有"连续比对异常计数 → 触发"**：`strike`/`strike_pause_mono`（原 316-317 行）是删旧 ±1s
   自校准 toggle 后遗留的**死变量**，全文无引用。
2. **0.5~1.0s 死区**：样本被门控丢弃（`>0.5s`），而 coarse 路径需 `>1.0s` —— 落在这个区间的时钟误差
   既不进 SHM 也不被纠正，看门狗重启也无法自愈（重启后阈值依旧够不到）。
3. **`bts.tv_nsec = 0`**：coarse 步进只能把钟写到整秒，**固有 0~1s 误差**，可能直接把时钟送进死区。
4. **coarse 路径无仲裁**：样本路径有 `|S_round - S_chain| ≤ 1s` 检查，coarse 路径直接信任 `anchor_S` 就写钟。
5. 同一文件三处注释互相矛盾（头注释 `>1.5s`、行内 `>0.5s`、实现 `>1.0s`），且头注释描述的是已被替换的
   "发粗样本"旧设计。

### 4.2 本轮改动（已完成并编译通过，**未部署**）

| 改动 | 说明 |
|---|---|
| **锚点序列仲裁** | 新增 `anchor_seq`：只在锚的秒值**连续递增 ≥3 次**时才允许写钟。源跳变时绝不写钟 |
| **死区自愈** | 门控时 `strike++`，正常入样清零；`strike ≥ -M`（默认 10）触发强制步进 |

| **CLI** | `-M <n>` 连续门控阈值、`-X <n>` 小时步进上限 |
| **注释修正** | 头注释与行内注释改为与实现一致 |

## 过程中我引入并修掉的两个缺陷（如实记录）

1. **"相位保持步进"是错的**：我把动作改成 `clock_settime(now + off)`，但 `off` 来自
   `S_round = round(边沿本地时间)`，它天然带 ±0.5s 量化；把量化值当增量应用会**保留**（甚至放大）
   相位误差。实测表现为恢复服务后出现 **±1.000s 交替步进循环**（每 11 秒一次、符号相反）。
   修复：触发判定仍用边沿实测偏差，**动作改回整秒对齐**（`tv_sec = anchor_S + edge_delta - 1`，`nsec = 0`）
   —— 原来的 `nsec=0` 并非"粗疏"，它同时承担了**强制相位归零**的职责。
   另加**符号一致性保护**：门控偏差符号翻转即清零 strike，交替偏差绝不触发步进。
2. **用 `anchor_S − now_rt` 当偏差是错的**：NMEA 语句在秒内某时刻到达，这个量混入了**到达相位**，
   正确时钟也会算出非零值。改用 `emit_sample` 里基于 **PPS 边沿**的实测偏差（新增 `last_off_mono` 记录时效）。

## 新发现：整秒指派使亚秒相位误差不可见（**先于本轮存在**）

独立测量（Windows `w32tm` 走 NTP 协议、含 RTT 补偿）与板端自述**长期不一致**：

| 时刻 | 板端自述 | 独立实测 |
|---|---|---|
| 15:42 | `good=1 offset_us=31`、chrony `System time 0.9µs`、`#* PPS` | **+0.512s** |
| 15:45 | `good=1 offset_us=-10`、chrony `System time 1ns`、`#* PPS` | **−0.4995s** |

机理：`S_round = round(edge_local_time)` 把边沿的本地时间归到**最近整秒**，于是
`off = S_round − rt_e` 恒落在 ±0.5s 内 —— **无论真实相位误差多大**。chrony 忠实锁定这个自洽参考，
于是系统稳定在一个**整体偏移可达 ±0.5s** 的状态并报告 µs 级健康。

影响：
- 交付文档中"µs 级"的表述是 **chrony 内部自洽口径**，不等于**绝对 UTC 精度**；
  绝对相位受 `round()` 量化限制，且有约 ±0.5s 的**锁定不确定性**。
- 本轮注入把相位推过 0.5s 边界后，链条即锁定在 −0.5s 一侧；手工校正相位后又被拉回边界，
  说明该边界是当前算法的**稳定不动点**。
- 本次注入 `-0.7s` 被链条测成 `1.703s`、`-1.5s` 测成 `2.503s`，也是同一量化在起作用（整秒 + 相位）。

**建议的后续修复方向**（本轮未做，需另行设计验证）：
让 `S_chain`（由 NMEA 绝对秒 + 边沿计数推出的真值）在 `anchor_seq` 良好时**参与相位校正**，
而不是仅在 `|S_round − S_chain| > 1` 时才启用 —— 这样亚秒相位误差才能被持续消除，
绝对精度才真正由 TOD 源决定。

## 板端当前状态

`pps_tod` / `pps_tod_watchdog` / `chrony` / `ntp-stats.timer` / `ntp-nic-monitor` 全部 active；
chrony 锁定 `#* PPS`；守护进程无门控、无步进、`reset_state=OK`。
**但绝对相位约 −0.5s**（自洽但非绝对正确），这是上面那条既有设计限制，非本轮引入。

# 附录五：同网段 allow/deny 共存（2026-09-17 17:30）

## 背景

deny 联动测试时撞出一处真实可用性问题：**给已有 allow 的网段加 deny 被拒**（`规则已存在`），
因为 `ntpmon_acl_find()` 只按 CIDR 匹配、不看动作。想翻转一个网段的放行状态必须**先删后加**，
而删除会重启 chronyd —— 计数器归零 + 约 1 分钟重锁 PPS。

chrony 本身支持共存（按最长前缀匹配，**等前缀长度下 deny 优先**），所以这是 Web 层的限制而非 chrony 的限制。

## 改动（四处联动）

| 位置 | 改动 |
|---|---|
| `src/ntpmon.h` / `ntpmon.c` | `ntpmon_acl_find()` 增加 action 参数（NULL = 只比 CIDR，兼容旧调用） |
| `src/ntpmon.c` `ntpmon_acl_apply()` | 传参由"仅 add 带动作"改为"动作非空就带"，使 remove 也能定向下发 |
| `src/ntpmon.cgi.c` | 查重改为按 (action, CIDR)；remove 允许带动作并校验其合法性；不带动作时用匹配到的规则动作补全 |
| `chrony_acl_apply.sh` | `remove [allow\|deny] <CIDR>`；不带动作时退回旧的"allow 优先"行为 |
| `www/control_panel.html` | 删除按钮与确认框携带动作（`aclRemove(action, cidr)`） |

## 实测验收

```
变更前:  chronyd 启动 17:16:49, allow 192.168.1.0/24, accheck=208 allowed
一步添加 deny 192.168.1.0/24  →  {"status":"ok","message":"规则已添加并即时生效"}
变更后:  chronyd 启动 17:16:49（未变）, serverstats 15,0,20,0,0（未归零）,
         accheck 192.168.1.121 → 209 denied,  accheck 192.168.137.11 → 208 allowed
         ACL 文件: allow 与 deny 两行共存
UI:      同网段两行（allow 绿 rgb(74,138,90) / deny 红 rgb(196,80,80)），
         删除按钮分别携带 aclRemove('allow',…) 与 aclRemove('deny',…)
拦截实效: 注入 10 包 → OUTPUT 219→219、ntp_hits 15→15（均未增长）
清理:    remove deny 192.168.1.0/24 → 仅删 deny、allow 保留、accheck 恢复 208 allowed
```

**关键收益**：翻转网段放行状态现在**不重启 chronyd、计数器不清零**（此前必然付出这个代价）。

测试：`test_gate.sh` **171 项全绿**（新增 28h 同网段异动作放行、28h2 精确重复仍拒、28i 删除带解析出的动作、
28i2 动作不匹配不误删、28i3 非法动作拒绝）。

## 边界

- 删除**仍然**会重启 chronyd（chrony 3.4 无运行时删规则命令），这一点没变
- 表格会出现同网段两行：功能正确但视觉上需要用户理解"等前缀下 deny 优先"
- `sudoers` 的 `remove *` 通配已覆盖新参数形式，无需改动

# 附录六：eth0 / eth1 NTP 压测（2026-09-17 18:50）

## 压测器

`ntpburst.py`（Windows 侧运行，48 字节标准 NTP v3 client 请求）：
- 支持"全速突发"与"限速"两种模式。限速按 ~20ms 批次发送 + 忙等收尾，
  因为 Windows 的 sleep 粒度（~15ms）远粗于 100µs 的包间隔；
- **报告实际达成速率**，不假设一定发得出去。

## 结果

### 达成目标：10k/s 每口（含双口并发）

| 场景 | 实际发出 | 内核送达 | chrony 处理 | 应答 |
|---|---|---|---|---|
| eth0 单口 10k/s ×1s | 9973 pps | **10000/10000** | +10000 | **100%** |
| eth1 单口 10k/s ×1s | 9942 pps | **10000/10000** | +10000 | **100%** |
| **双口并发**各 10k/s | 9882 / 9863 pps | **20000/20000** | +20000 | **100%** |

零丢失、零串扰（另一口的计数完全不动），板端空闲 CPU 仅从 72% 降到 82%。

### 上限探测：约 34,500 请求/秒（聚合）

| 目标 | 送达 | chrony 处理 | 应答率 | 丢在哪 |
|---|---|---|---|---|
| 20k/s 各口 | 40000/40000 | 34526 (86%) | 86% | 内核 UDP 收包队列 |
| 50k/s 各口 | 54079/100000 | 35737 | 36% | PC 侧 + 内核队列 |

**丢包位置已钉死**（20k/s 那轮，用 `/proc/net/snmp` 正确列号）：

```
内核 UDP InDatagrams      +34526   ← 实际投递给 socket
chrony 处理(ntp_hits)     +34526   ← 收到的全部处理
chrony 发出(OutDatagrams) +34526   ← 处理多少回多少
内核 RcvbufErrors          +5474   ← 收包队列溢出丢弃
缺口 5474 == RcvbufErrors 5474
```

结论：**chronyd 自身从不丢包**（收到 = 处理 = 应答），瓶颈是**它单线程的收包循环来不及排空
socket 队列**，超出部分在内核 UDP 层被丢弃。~34.5k/s 是这块板子的实际天花板。

### 附加发现：全速突发会在 PC 侧丢一半

不限速时压测器可达 **104k pps**，但 10k 包只送达 4841/5237（48%/52%），
而**板端网卡 `rx_dropped/rx_missed/rx_errors` 全为 0** —— 丢失发生在 PC 的协议栈/驱动，
不是板子。所以"突发打不满"不代表板子不行，**压测必须限速才有意义**。

### 监控链路在压测下完全可信

用户态 AF_PACKET 抓包数与内核 iptables 计数**逐包相等**：

| 速率 | eth0 捕获率 | eth1 捕获率 |
|---|---|---|
| 各 10k/s | 100.0% (10000/10000) | 100.0% (10000/10000) |
| 各 20k/s | 100.0% (19769/19769) | 100.0% (19748/19748) |

即压测不会让监控数字失真——柱状图、客户端明细在 20k pps 下依然逐包准确。

### UI 联动

压测后面板如实反映：eth0 近1h 请求 147555 / 应答 127285（**86%**），
eth1 141621 / 120850（**85%**）—— 应答率低于 100% 正是超限突发被内核丢弃的体现，
不是 UI 错误。柱状图与趋势图同步增长。

## 对授时子系统的影响

压测期间与之后，`pps_tod` / 看门狗 / chrony 全部 active，`consec_gated=0`、`forced_resets=0`，
压测**未对授时链路造成任何额外影响**。

> 注：压测时接收机本就处于**失锁状态**（17:38 起无 1PPS 与 NMEA，`#? PPS` Reach 0，
> 看门狗已 3 次重启用尽转 DEGRADED）。这是**独立的既有故障**，与压测无关；
> 板子时间因此自由运行，实测偏慢约 1.06 秒。需检查天线/接收机。

## 结论与建议

- **10k/s 每口（含双口并发 20k/s）可稳定承载，零丢失**，与既有测试结论一致；
- 实际天花合约 **35k 请求/秒**（聚合），再往上会被内核 UDP 队列丢弃；
  chronyd 单线程收包是该上限的根因，调大 `rmem_max` 只能拖延、不能提高持续速率；
- 压测**必须限速**：全速突发（104k pps）的瓶颈在 PC 侧，测不出板子能力；
- 监控链路（iptables + 守护进程）在 20k pps 下逐包准确，**压测不影响监控可信度**。
