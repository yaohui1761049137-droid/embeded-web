# NTP 请求量爬升压测报告 — 2026-09-18

> 需求：对 eth0 与 eth1 持续 10 分钟注入 NTP 请求；单位时间请求量**由低到高**爬升；
> 当**应答率下降到 80%** 时，单位时间请求量再**由高到低**回落。
> 结论先行：**需求完整执行**。触发点 20,000 pps/口（聚合 44,500 pps 实测，应答率 79.2/79.4%），
> 回落后在 16,000 pps/口（聚合 33,000 pps）恢复 ≥95%，全程 10 分 08 秒，chrony/授时全程健康。

## 1. 测试环境与路径

| 项 | 值 |
|---|---|
| 被测板 | LubanCat 2N（RK3568，Debian 10，kernel 4.19.232），chrony 为 NTP 服务端 |
| eth0 | `192.168.137.100/24` ↔ PC USB 百兆网卡（源 `192.168.137.11`） |
| eth1 | `192.168.1.150/24` ↔ PC 板载千兆（源 `192.168.1.121`） |
| 注入端 | Windows Python 3.10 忙等节奏发包（`ntpflood.py`），500/5k/20k pps 实测节奏误差 <0.1% |
| 应答率口径 | 板端 iptables 逐口 INPUT（请求）与 OUTPUT（应答，`spt:123`）增量之比 |
| 交叉验证 | `chronyc serverstats`（hits/drops）、`/proc/net/snmp Udp RcvbufErrors`、`/sys/class/net/*/statistics` |

ACL 前置确认：两个测试源均在 `/etc/chrony/acl-web.conf` 的 allow 网段（137.0/24、1.0/24）。
压测前基线：双口 INPUT=OUTPUT 逐包相等（低负载应答率 100%）。

## 2. 阶梯设计与执行时间线

- **爬升（阶段 A）**：500 → 1000 → 2000 → 4000 → 8000 → 16000 → 20000 → 24000 pps/口（双口对称），每档最长 40 秒，每 5 秒采样。
- **触发规则**：任一口**连续两个有效采样窗**应答率 < 80% 即停止爬升。
- **回落（阶段 B）**：16000 → 12000 → 8000 → 6000 → 4000 → 3000 → 2000 → 1000 → 500 pps/口，每档 25 秒；连续两窗恢复 ≥95% 时记录恢复点。
- 实际执行：16:00:12 开始，16:05:18 触发，16:10:20 结束（**10 分 08 秒**）。

## 4. 丢失定位（对照实验，非需求但关键）

恒定 12,000 pps/口 注入 30 秒、每 2 秒五点采样（INPUT / OUTPUT / chrony hits / RcvbufErrors / chrony socket）：

- 每窗 `chrony hitsΔ / INPUT Δ` 与 `OUTPUT Δ / INPUT Δ` **逐窗相等**（77.9/77.5、92.8/92.5、59.0/59.7…），
  `hitsΔ − OUTPUT Δ` 合计仅 −125（边界误差）→ **chrony 收到即必答，回复路径 1:1，无回复侧丢失**。
- `Udp RcvbufErrors` 全程恒定（0 增量）→ **内核 socket 接收队列从未溢出**；`chrony ntp_drops = 0`；
  网卡 `rx_dropped/rx_errors = 0`。
- 结论：未回复的请求消失在 **iptables INPUT 计数之后、chronyd 接收之前**，且不走任何已有的丢包计数器，
  在时间上呈**突发性**（恒定速率下各窗 59%↔92% 摆动），不是纯速率函数。
- 暂停 `ntp-stats.timer` 复测：8k 档 97.6/97.7%（与主测 96.8% 一致，可复现）；
  12k 档 84.7/84.8%（主测同档 63.5–72.5%，同为突发波动）。

**未定论**：该"静默丢失"的精确内核机制未查明（候选：板端 4×A55 在高 pps 下 softirq 与
AF_PACKET 采集守护进程争抢导致的接收路径瞬时停滞；RK3568 USB/网卡中断合并影响）。
已排除：chrony 主动丢弃（drops=0）、内核 UDP 队列溢出（RcvbufErrors 恒定）、网卡丢包、计数器重置
（规则无重复，测试前后计数器单调递增；窗口总增量与分钟 CSV 跨度增量自洽）。

## 5. 与交接文档数据的差异说明

handoff（2026-09-17）记录"实测上限约 34,500 请求/秒（聚合），chronyd 零丢失"。
本次在 33k 聚合处测得 99.8%（一致），但 16.6k 聚合处即出现 ~3% 静默丢失，
且 44.5k 聚合处应答率 79% 时内核 RcvbufErrors 仅 +477（0.2%），与"socket 队列溢出"模型不符。
两次测试的负载形态不同（本次为双口对称、绝对节奏 1:1 占空比；前者为前次会话的突发压测器），
建议把"34.5k 上限"理解为突发压测口径，而非本口径下的拐点。

## 6. 过程中修复的问题（对复跑有用）

1. **整分采样窗作废**：板端 `ntp-stats.timer` 每分钟 `*:00` 触发，其执行窗口内
   OUTPUT 计数读数会瞬间回退（读到的增量出现 27 万包的负值），任何横跨 `:00±2s`
   的采样窗必须作废（脚本已内置 skip + 计数器回退自动重建基线）。
2. **Windows 发包进程管理**：`powershell` 包装进程被 kill 时 python 子进程会孤儿化继续发包
   （首跑累积 18 个残留发包器叠加污染数据）。改为 `Start-Process -PassThru` 记 PID +
   `Stop-Process -Id` 定向杀 + 发包端自然超时兜底；每档结束校验 PID 并打印发包端 stderr。
3. **`/proc/net/snmp` 读取陷阱**：`grep -A1 '^Udp:' | tail -1` 会取到 `UdpLite:` 的**表头**行
   （字段名而非数值），必须按"表头学列位、值行取数"的方式解析，否则数值列会混入字符串
   `SndbufErrors`（`set -u` 下直接崩）。
4. **日志 pps 显示**：早期版本用"睡眠前时间戳差"做窗长，分母少算快照耗时（~1.5s），
   显示 pps 偏高约 25%；报告内数值已改用相邻采样 epoch 差重算（应答率为比值，不受影响）。
