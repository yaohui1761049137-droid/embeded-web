## 2. ⚠️ 操作环境陷阱（接手前必读，能省几小时）

### 2.1 WSL 无法访问 `192.168.137.0/24`，必须走 Windows 侧

WSL2 是镜像网络模式，PC 的 `以太网` 同时有 `192.168.137.1` 与 `192.168.1.121`，导致 WSL 对
`192.168.137.100` 选错源地址（`src 192.168.137.1`），TCP 完全不通（WSL 到 WLAN 网关是通的，
只这个网段坏）。**Windows 侧一切正常**（ping/22/443 都通）。

**可用做法**：WSL 通过 `powershell.exe` 互操作调用 Windows 的
`ssh.exe`（OpenSSH 9.5p2）/ `scp.exe` / `curl.exe` / `Python 3.10`
（`C:\Users\YAO\AppData\Local\Programs\Python\Python310\python.exe`）。

免交互 SSH 的关键是 **`SSH_ASKPASS` + `SSH_ASKPASS_REQUIRE=force`**，askpass 是一个内容为
`@echo root` 的 `.cmd`。骨架：

```bash
# bssh.sh —— 在板端跑一段 sh（base64 传，避免所有引号问题）
payload=$(cat); printf '%s' "$payload" | base64 -w0 > "$WINDIR/payload.b64"
powershell.exe -NoProfile -File 'C:\...\bssh.ps1' -B64File 'C:\...\payload.b64' -Board 192.168.137.100
# bssh.ps1 内容：
#   $env:SSH_ASKPASS=<...>\askpass.cmd; $env:SSH_ASKPASS_REQUIRE='force'; $env:DISPLAY='localhost:0'
#   $b64=(Get-Content -Raw $B64File).Trim(); ssh -T -q -o StrictHostKeyChecking=no root@$Board "echo $b64 | base64 -d | sh"
```

- **命令行有长度上限（约 32KB）**：传大文件必须用 `scp.exe`（同样吃 askpass），不能塞进命令行。
  本会话首次传 24KB 源码时就撞上过这个限制。
- `test_ntp_nic.sh --transport winrelay` **已把上述机制实现进仓库**，可直接参考或复用。

### 2.2 PC 的时钟不可信

Windows 时间服务**未运行**（`0x80070426`），PC 自身**快约 0.91 秒**
（对 `ntp.aliyun.com` / `time.windows.com` / `pool.ntp.org` 三个独立源一致测得）。

**任何"板子偏多少"的绝对时间测量都会被这个偏差污染。** 本会话曾据此错误地报告"板子偏慢 1.06 秒"，
实际换算后约 −0.19 秒。**测量前先修好 PC 的时间服务，或明确记录基准的偏差。**

### 2.3 这块板子的 `AF_PACKET` 只交付入向包

实测：注入 9 包、chronyd 实发 9 包、`AF_PACKET` 的 outgoing 计数为 **0**。
所以出向（应答）**必须**用 iptables OUTPUT 计数，不能靠抓包。内核 4.19 也没有
`PACKET_IGNORE_OUTGOING`（4.20+ 才有），出入向靠 `sockaddr_ll.sll_pkttype` 区分。

## 3. 本会话做了什么

### 3.1 需求一：系统日志

**判定**：日志在写但没有查看功能；核验还发现板端日志已失控。

**核验发现**（详见 `system-log-audit-2026-09-17.md`）：
- `/var/log` 积压 **694 MB**。主因是 **hostapd 缺 `/etc/hostapd/hostapd.conf` 却 enabled**，
  每 2 秒失败写 4 行（约 10 MB/天，占 `daemon.log` 行数的 **56.8%**）
- **logrotate 日期记账失真**：板子无 RTC 电池、时钟在 2017/2019/2022/2026 间跳变，
  状态文件里所有条目都是同一次开机时刻，`logrotate -d` 认为"刚轮转过"而跳过
- **cron 包从未安装**（`dpkg -l` 显示 `un cron`）→ 只有 `/etc/cron.d/*` 不执行

**实现**：`src/log.cgi.c`（新）+ 前端「系统日志」Tab（root 专属）。
安全模型：**路径由固定 id→path 表推导**（穿越在结构上不可能）、只读、无 fork/exec、
**只读文件尾部 256KB**、行数上限 500、`LOGVIEW_ROOT` 可覆盖便于离线测试。

**治理（已执行）**：停用 hostapd → `logrotate -f` 规范轮转 → `gzip -9` 压缩归档
→ **694 MB 降到 83 MB**；RTC 每 6h 持久化由失效的 `/etc/cron.d` 条目改为
`pps_tod_rtc.{service,timer}`（`OnCalendar=*-*-* 00/6:00:00`）。

**两处更正**（已写入文档）：初版写"`cron.daily` 也不执行"**是错的**（它一直由
`anacron.timer` 驱动）；初版把 logrotate 的问题归因于 cron **也是错的**（纯粹是时钟跳变）。

### 3.2 需求二：逐网口授时监测

**实现**：`ntp_nic_monitor.c` + `ntp-nic-monitor.service`（新）+ 前端两块面板 + 页级时间范围开关。
- 入向 AF_PACKET（客户端身份）／出向 iptables OUTPUT（应答率），原因见 §2.3
- 客户端表 1024 槽固定开放寻址哈希，**零动态分配**；每口 Top 32；TTL 24h 由前端按窗口过滤
- 快照 `/var/db/ntp_nic.json` 每 5 秒 **tmp+rename 原子写**
- 桶 1440（覆盖 24h），1h/5h/24h 由**同一组环形的后缀求和**得出；JSON 只输出尾部 60 个桶
- `src/ntpmon.c` 把守护进程的 JSON **原样嵌入** stats 响应的 `nic` 键（不写 C 解析器），
  缺失降级 `ok:false`、超缓冲降级 `too_large`（而非输出被截断的非法 JSON）

**实测**：
- 注入归属逐层一致（iptables → CSV → CGI JSON → 浏览器 uPlot 实例数据）
- **压测 10k/s 每口、双口并发 20k/s：100% 送达、100% 应答、零串扰**
- **监控链路与内核计数逐包相等**（10k/s 与 20k/s 下均 100.0%）
- **实测上限约 34,500 请求/秒**（聚合）：chronyd 自身零丢失，瓶颈是它单线程的收包循环
  来不及排空 socket 队列 → 超出部分被内核 UDP `RcvbufErrors` 丢弃
- **压测必须限速**：不限速时压测器可到 104k pps，但 10k 包只送达约 50%，
  而板端网卡 `rx_dropped/rx_missed/rx_errors` 全为 0 —— 丢在 PC 侧

### 3.3 需求三：chrony 黑白名单

**判定**：已实现，**Web 是受管路径**。本轮补齐两件：
1. **边界文档化**（`ntp-monitor.md` §2.1）：console 手工 `chronyc` 的规则**不持久、不入审计、
   表格看不到也删不掉、重启即失**
2. **同网段 allow/deny 共存**（§2.2）：此前给已有 allow 的网段加 deny 被判"规则已存在"
   （`ntpmon_acl_find` 只比 CIDR），翻转网段放行状态必须先删后加，而删除会重启 chronyd
   （计数归零 + 重锁 PPS 约 1 分钟）。chrony 本身支持共存（**等前缀下 deny 优先**），
   故匹配改为按 **(action, CIDR)**，remove 支持带动作定向删除。

**实测**：一步加 deny 成功、**chronyd 未重启、`serverstats` 未归零**、`accheck` 生效；
UI 同网段两行各自携带动作、不会误删。

### 3.4 需求四：TOD 时码比对

源码在仓库外：`/mnt/c/Users/YAO/Desktop/codex_store/PPS_TOD/pps_tod.c`
（原件已备份 `pps_tod.c.orig-20260917`）。改动 **+93/−24 行**。

**修复的四处缺口**：
1. **没有"连续比对异常 → 触发"**：`strike`/`strike_pause_mono` 是删旧逻辑后遗留的**死变量**
2. **0.5~1.0s 死区**：样本被门控丢弃（>0.5s）而 coarse 路径需 >1.0s，落在这个区间的时钟误差
   既不进 SHM 也不被纠正，**看门狗重启也无法自愈**
3. **`bts.tv_nsec = 0`** 使步进只能写到整秒（固有 0~1s 误差）
4. **coarse 路径无仲裁**：样本路径有 `|S_round − S_chain| ≤ 1s` 检查，coarse 路径直接信任 `anchor_S`

**改动**：锚点序列仲裁（锚的秒值连续递增 ≥3 次才允许写钟）／死区自愈（连续门控 ≥ -M 次强制步进，
带**符号一致性保护**）／步进动作保持**整秒对齐**（`nsec=0` 同时承担相位归零职责）／
小时配额 `-X`（超限转 `CAPPED` 停止写钟）／状态文件新增四个字段／CLI `-M`/`-X`／注释修正。

**故障注入 4 项全过**：−0.7s 走 stuck 路径（`consec` 累加到 10 → `forced clock step`）、
−1.5s 走 urgent 路径（2 秒即纠正）、配额闸（超限后不再写钟）、正常态回归。

**⚠️ 遗留限制（设计固有，先于本会话存在）**：
`S_round = round(边沿本地时间)` 把边沿归到最近整秒，于是 `off = S_round − rt_e` **恒落在 ±0.5s 内
—— 无论真实相位误差多大**。chrony 忠实锁定这个自洽参考，系统会稳定在**整体偏移可达 ±0.5s** 的状态
并报告 µs 级健康。**交付文档里"µs 级"是 chrony 内部自洽口径，不等于绝对 UTC 精度。**
修复方向：让 `S_chain`（NMEA 绝对秒 + 边沿计数推出的真值）在 `anchor_seq` 良好时参与相位校正，
而不是仅在 `|S_round − S_chain| > 1` 时才启用。**需单独设计 + 故障注入验证。**

## 8. 给下一个 agent 的建议

1. **先读 §2 的环境陷阱**，尤其 §2.1 的通道搭法 —— 否则第一步就会卡在"SSH 连不上"。
2. **改动前先跑 `./test_gate.sh`** 确认基线 171 项全绿，改完再跑一遍。
3. **部署二进制用 `mv` 而不是 `cp`**（§2.4），CGI 编译在 `/root/build/src/`。
4. **改时间窗口/容量这类常量时，先看 §6 的表** —— 有几处是强耦合的，
   本会话踩过"一行里混了两个时间基"导致读数自相矛盾的坑。
5. **别轻易相信单一参照物**：本会话两次误判（cron、时钟偏差）都源于把假设当事实。
   §2.2 是活生生的例子——基准 PC 自己就不准。
6. **文档里的"⚠️ 更正"段落是有意保留的**，不要清理成一致的叙述——那些是排查线索。
