# 各网口 NTP 流量监控 — 实测报告

> 2026-09-17 · 被测板卡 LubanCat 2N（192.168.137.100 / 192.168.1.150，aarch64，kernel 4.19.232）
> 被测功能：`docs/ntp-monitor.md` 描述的「服务监控及报警」Tab 各网口柱状图
> 复现脚本：`test_ntp_nic.sh` · 原始证据：`docs/ntp-nic-test-2026-09-17/`

## 1. 结论摘要

**逐网口计数功能正确。** 在 eth0（192.168.137.0/24）与 eth1（192.168.1.0/24）两条独立链路上做受控注入，
四层证据链（物理收包计数 → iptables 计数 → CSV 落盘 → CGI JSON → 浏览器渲染数值）逐项吻合，
**零串扰**；并发注入下两口径独立归属；未接线的 eth2/eth3 全程恒为 0。

同时实测出三条**文档未写明或表述不够精确**的语义：

1. **被 ACL 拒绝的请求对 chrony 完全不可见** —— `ntp_hits` 和 `ntp_drops` 都不会增加，只有 iptables 网口计数能捕获。
2. **网口计数是纯端口级包计数** —— 不校验 NTP 协议内容，任意 UDP/123 载荷都会计入。
3. **chronyd 重启与 iptables 计数完全解耦** —— 前者归零、后者不回退，前端折线出现断点而柱状图不受影响。

## 2. 被测实现的约束（决定了测试方法）

```
ntp-stats.timer(每分钟整点) → ntp_stats_sample.sh
   ├─ iptables -I INPUT -i ethN -p udp --dport 123 -j ACCEPT   （只计数，幂等自愈）
   └─ chronyc -c serverstats                                   （chrony 全局 5 计数器）
        → /var/db/ntp_stats.csv
浏览器 ←60s轮询→ ntpmon.cgi?action=stats ← 读 CSV
```

计数规则挂在 **INPUT 链**上，因此只有"从外部、经该物理网口进来、目的地址是本机"的 UDP/123 包才计入该口。
板子自发包走 OUTPUT 链不计；发往本机另一网口地址的包被内核走 lo 也不计。
**每个网口必须有真实对端设备往它发包**，否则归属性无从验证。

## 3. 测试环境与拓扑

```
    PC (Windows + WSL2)
  ┌────────────────────────────┐
  │ 以太网    192.168.1.121/24 │──── 直连 ──── 板 eth1  192.168.1.150/24  (MAC 8e:a3:d4:8d:e3:28)
  │          192.168.137.1/24  │                carrier=1  speed=100
  │ 以太网 2  192.168.137.11/24│──── 直连 ──── 板 eth0  192.168.137.100/24 (MAC 8a:a3:d4:8d:e3:28)
  └────────────────────────────┘                carrier=1  speed=100
                                                板 eth2  192.168.7.150/24  carrier=0  未接线
                                                板 eth3  192.168.6.150/24  carrier=0  未接线
```

两条链路分属**不同子网**，且均为点对点直连 —— 这是本次能做精确归属验证的前提。

### 3.1 环境陷阱一：PC 双网卡同网段（已规避）

PC 的 `以太网` 同时配了 `192.168.137.1/24` 与 `192.168.1.121/24`。
这导致 Windows 对 `192.168.137.0/24` 存在**两条等价路由**（`以太网` 与 `以太网 2`，metric 均为 256/35），
目的地址 192.168.137.100 的包可能从错误的网卡出去、从板子的 eth1 进来。

板子侧也有对称的 ARP flux：`arp_ignore=0`（默认）时 eth1 会为 eth0 的地址应答 ARP，
在 Windows 邻居表里留下了 `192.168.137.100 → 8E-A3-D4-8D-E3-28（eth1 的 MAC）` 这条记录。

**规避手段：发送端绑定源地址**（`socket.bind((src, 0))`）。Windows 按源地址选路，
绑到 `192.168.137.11` 必然走 `以太网 2`，绑到 `192.168.1.121` 必然走 `以太网`。
测试脚本第 1 节的探针会用**物理收包计数**先证伪归属，不成立就立即终止。

### 3.2 环境陷阱二：WSL 镜像网络无法直达 192.168.137.0/24

WSL2 为镜像网络模式，`eth1` 同时承载了宿主的 `192.168.137.1` 与 `192.168.1.121`。
`ip route get 192.168.1.150` 选出的源地址是 `192.168.137.1`（**跨子网的错误源地址**），
导致 TCP 完全不通（ping/TCP22/443 全超时），而 Windows 侧一切正常。

- 规避：`curl --interface 192.168.1.121` 可通（HTTP 200），说明只是源地址选择问题；
- 最终采用 **Windows 侧通道**：宿主的 OpenSSH 9.5p2（`SSH_ASKPASS` 免交互）+ curl.exe + Python 3.10，
  由 WSL 通过 `powershell.exe` 互操作驱动。`test_ntp_nic.sh` 的 `--transport winrelay` 即此路径。
- 浏览器验证用 WSL 侧 Playwright + Chromium 152，经一个绑定正确源地址的本地 TCP 隧道访问板端 HTTPS。

### 4.2 ACL 交互语义（核心发现）

用 Web API 加一条 `deny 192.168.1.121/32`（精确匹配压过 `allow 192.168.1.0/24`），
**同一源 IP、同一目标、同样 70 包**，唯一变量是 ACL：

| | P3（允许） | P5（拒绝） |
|---|---|---|
| `chronyc accheck` | 208 Access allowed | 209 Access denied |
| iptables e1 | **+70** | **+70** |
| eth1 物理收包 | +70 | +70 |
| `ntp_hits` | **+70** | **+0** |
| `ntp_drops` | +0 | **+0** |

**结论：被拒绝的请求在 chrony 的 serverstats 里完全隐形**（既不进 hits 也不进 drops），
只有 iptables 网口计数能捕获。这从反面证明柱状图选择 iptables 路线是**唯一**能看到被拒流量的方案；
`docs/ntp-monitor.md` 中"含被 ACL 拒绝的请求"这句建议加注"chrony 侧完全不可见"。

同时验证了 ACL 新规则的**即时生效**：加规则后 `chronyc accheck` 立刻返回 209，
而 chronyd 进程启动时间未变（未重启）。

### 4.3 归零与断点语义

通过 Web API 删除规则会触发 `systemctl restart chrony`（chrony 3.4 无运行时删除命令）：

| 指标 | 重启前 | 重启后 |
|---|---|---|
| `chronyc serverstats` | `228,0,806,0,0` | `0,0,1,0,0` |
| chronyd 启动时间 | 10:07:13 | 11:00:47 |
| **iptables e0 / e1** | **228 / 195** | **228 / 195（不变）** |
| `series.c` 尾部 | `[…,228,228]` | `[…,228,228,0,0,30]` |
| `series.m` 尾部 | — | `[…,0,0,`**`-1`**`,0,30]` |

- CSV 断点行 `1789614060,0,0,5,0,0,228,195,0,0`：chrony 列归零，网口列原样保留。
- 后端把 `d < 0` 的采样点写成 `m = -1`，前端转 `null` → 折线断开（浏览器实测 4 个 null 点）。
- 重启后重新注入 30 包，`c` 从 0 涨到 30 —— 计数从零重新累积且被拒规则确已解除。
- PPS 源在约 1 分钟后重新锁定（`#? PPS` → `#* PPS`），符合文档描述。

## 5. 发现的问题

### 5.1 【中】柱状图最右侧分类标签被裁切

`control_panel.html:1346-1354` 的 x 轴把 4 个分类标签居中画在柱子上，
最后一个 `eth3` 超出绘图区右边界被切掉，**截图里显示为 `eth:`**，用户看不到完整的网口名。

- 影响：纯显示问题，数值正确。
- 建议：给 x 轴加左右内边距（`padding: [10, 10, 0, 0]` 的右值调大），或把分类轴的 `splits` 收紧到 `[0.5, 1.5, 2.5, 3.5]` 让标签内移。

### 5.2 【中】"含被 ACL 拒绝的请求"表述不够精确

实测证明被拒请求在 chrony 侧**完全不可见**（hits 与 drops 都不计）。
当前措辞会让读者以为 chrony 的 `ntp_drops` 也能反映一部分，实际不是。
建议在 `docs/ntp-monitor.md` 表格与前端 `chart-eth-meta` 文案中明确"chrony 侧完全不可见，仅 iptables 计数可见"。

### 5.3 【低】网口计数是纯端口级，不校验协议

10 个非 NTP 载荷（`NOT-AN-NTP-PACKET-*`）发到 UDP/123 后 `e0 +10` 而 `ntp_hits +0`。
正常 NTP 客户端不会造成误判，但端口扫描、畸形包、其他误发到 123 端口的流量都会进柱状图。
如果这个语义对使用方重要，建议在图注里写明"按端口计数，不解析 NTP 协议"。

### 5.4 【低】规则被单独删除后重建会静默清零累计值

采样器的自愈逻辑是 `iptables -C … || iptables -I …`：规则存在时不动（计数保留），
规则缺失时**新建**一条 —— 新规则的计数器从 0 开始。
所以"只删规则不重启设备"也会让该网口的累计柱值回落，而前端不会给出任何提示。

本次为保留 eth0/eth1 的累计证据，破坏性验证只在未接线的 eth2/eth3 上做（代码路径完全相同），
两口的规则均被采样器自动重建、CSV 正常写入。**5.4 属于代码路径的必然结果，未在活跃口上实测。**

### 5.5 【环境】测试环境的两处网络陷阱

见 3.1 与 3.2。均非产品缺陷，但会持续影响后续在这台机器上的板端调试，
建议在 `QUICKSTART.md` 里记一笔（尤其"WSL 到 192.168.137.0/24 不通、需走 Windows 侧"）。

## 6. 复现方式

```bash
# 默认（自动选择传输层；本地不可达时自动切到 Windows 转发）
./test_ntp_nic.sh

# 完整测试（含 70 秒静默基线观察）
./test_ntp_nic.sh

# 跳过静默基线，快速回归
./test_ntp_nic.sh --quick

# 指定地址与注入量
./test_ntp_nic.sh --board-ip 192.168.137.100 --eth1-ip 192.168.1.150 \
                  --src-eth0 192.168.137.11 --src-eth1 192.168.1.121 \
                  --n1 50 --n2 70
```

脚本前置要求（不满足会明确报错并终止）：

- 板端 4 条 iptables 计数规则在位（缺失时先跑一次 `/usr/local/bin/ntp_stats_sample.sh`）；
- `ntp-stats.timer` 处于 active；
- **两条链路分属不同 L2 网段**，且能通过绑定源地址强制出口网卡 —— 第 1 节的探针会先验证这一点。

脚本**不会**做的：不改网口配置、不重启 chrony、不删 ACL 规则。它只做注入 + 采样 + 断言，
会往 `/var/db/ntp_stats.csv` 追加真实采样行。
